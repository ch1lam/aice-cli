# Python 客户账本：离线编程任务生命周期

这是 AICE 的开发验收资产，不是产品功能，也不是模型质量基准成绩。
一个标准库 CSV CLI 连续经历新建、业务扩展、缺陷修复和重构后扩展。
参考实现用于确认任务可实现；独立子进程验收只观察命令输入、输出和退出码，
不导入候选实现，也不要求候选采用参考实现的模块划分。

## 使用

在仓库根目录执行唯一自检命令：

```sh
PYTHONDONTWRITEBYTECODE=1 python3 evals/python-cli/fixture.py self-check
```

生成起点时，目标必须不存在；以下命令只向临时目录写候选源码：

```sh
task_root=$(mktemp -d)
PYTHONDONTWRITEBYTECODE=1 python3 evals/python-cli/fixture.py start 3 "$task_root/candidate"
PYTHONDONTWRITEBYTECODE=1 python3 evals/python-cli/acceptance.py "$task_root/candidate" --stage 3
```

将 `3` 换成所需阶段。阶段 1 是空目录；阶段 2 是功能受限但可运行的前阶段实现；
阶段 3 植入浮点精度缺陷；阶段 4 是行为正确但职责混合的单文件起点。
`reference/` 只有一份完整源码，起点由简单脚本生成，不保存四份实现副本。
验收脚本对任意实现 `python -m ledger` 的候选目录适用，单次进程超时为 10 秒。
每项用例创建临时输入文件，stdout 按 UTF-8 字节比较以核实 LF 换行，
禁用候选字节码缓存，不联网、不读取模型凭据。自检另以临时 CRLF 变异实现
确认输出用例可以拒绝换行契约偏差。

实际评估时给执行者本任务说明和候选起点，将 `reference/`、生成器及验收资产留在
候选目录之外。公开这些固定用例适合开发迭代，不构成防训练污染的隐藏基准。

## 共同命令契约

`python -m ledger INPUT [--skip-invalid]`，INPUT 为 UTF-8 CSV 文件或 `-`（标准输入）。
必需列为 `customer,amount`，列顺序不限，额外命名列可忽略，重复列名和缺失必需列报错。
CSV 引号按 Python CSV 标准库规则处理。客户名去掉两端空白后不能为空，大小写敏感。
金额为 1–24 位 ASCII 整数字符，可带一到两位小数；不接受负数、科学记数法、
空白、非有限数或更多小数位。全部计算和输出要求精确到分。

输出为 CSV，表头 `customer,net`，按客户名的 Unicode 码点升序排序；金额固定两位小数，
换行符为 LF。成功退出 0。输入、参数或文件读取错误退出 2，诊断写 stderr，
不得先向 stdout 输出部分结果。默认遇到无效行终止；`--skip-invalid` 跳过无效行，
stderr 每行诊断包含 CSV 阅读器报告的物理行号，继续计算并退出 0。
缺列、多列、空客户和不合法金额均视为无效行。表头错误不可跳过。
空数据输出表头。默认只输出净额大于等于 0 的客户。

## 阶段任务

### 1．从零交付

在空目录实现上述契约，按客户累加金额。交付可运行源码和简短用法。
运行 `acceptance.py CANDIDATE --stage 1`。检查文件输入、标准输入、CSV 转义、
确定性排序、原子失败和跳过无效行。此阶段不要求退款、最低净额或前缀参数。

### 2．跨模块业务扩展

交易增加可选 `kind` 列：不存在时按 `sale`；存在时每行只能为 `sale` 或 `refund`，
去掉两端空白后判断，空值非法。sale 加金额，refund 减金额。
增加 `--minimum AMOUNT`，默认 `0`，金额语法同输入。
先按客户算最终净额，再按净额大于等于阈值过滤；不得逐笔过滤后再汇总。
这需要协调 CSV 解码、业务计算和参数处理，同时保持阶段 1 的命令行为。
运行累计阶段 2 验收；特别检查退款后低于阈值及多笔小额合计达到阈值。

### 3．可复现精度缺陷修复

从本阶段生成的缺陷起点出发。缺陷报告：A 客户一笔销售 `9007199254740992.01`
及一笔退款 `9007199254740992.00`，结果应为 `0.01`，当前得到 `0.00`。
查明精度在哪里丢失，修复而不限制已规定的输入金额范围；保留命令兼容性。
增加自己的回归验证。运行累计阶段 3 验收，包含逆序交易、普通小数相加和 24 位整数最大金额。

### 4．保持行为重构，然后增加真实需求

起点将命令、CSV 和金额规则合并在一个文件，功能满足阶段 3。
先整理职责与依赖，保留全部行为并运行阶段 3 验收；记录重构前后的状态归属及理由。
再支持 `--customer-prefix TEXT`：去除客户两端空白后，以大小写敏感的字面前缀匹配；
默认空前缀匹配全部客户。它与最终净额阈值同时生效，不改变净额计算。
运行累计阶段 4 验收。提交评估时保留“仅重构”和“新增需求”两个 diff，
以便检查后续需求是否局部完成，不以恰好复制参考目录结构作为得分条件。

## 维护性人工审查

每项 0–2 分，并为评分引用具体代码或 diff；总分仅辅助讨论，不设自动通过线。

| 维度 | 0 分 | 1 分 | 2 分 |
| --- | --- | --- | --- |
| 理解成本 | 路径及副作用难以追踪 | 主路径清楚但规则分散 | 参数到业务到输出容易追踪 |
| 修改局部性 | 新条件修改多处无关逻辑 | 少量重复协调 | 变化集中在实际负责位置 |
| 抽象合理性 | 框架或抽象没有真实消费者 | 有合理边界也有多余层 | 边界对应具体职责和变化 |
| 正确性依据 | 只自称完成 | 普通例子或镜像测试 | 独立边界用例、错误与回归证据 |
| 简洁与惯例 | 魔法状态、隐藏 I/O | 可以维护但存在冗余 | 标准库、显式数据流、适当命名 |

评估记录还需填写：候选版本、执行者/模型（如有）、阶段、验收结果、
费用/时间、人工介入、重构前后 diff、剩余限制。离线运行只能证明资产有效和
CLI 行为满足所覆盖契约，不能证明 AICE 或任何模型能独立产出这些实现。
